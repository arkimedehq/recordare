# LightMem: Lightweight and Efficient Memory-Augmented Generation (Fang, Deng, Xu, et al.; Zhejiang University / NUS, ICLR 2026, arXiv:2510.18866v4)
Read: full PDF text (main body, appendix A-D, all tables, complexity analysis); the repo README only via a summarising fetch, no source or prompts inspected; Code: https://github.com/zjunlp/LightMem (released; options `pre_compress`, `topic_segment`, `messages_use`, `metadata_generate`, `text_summary`, `index_strategy`, `retrieve_strategy`, `update: offline|online`; README says offline update is the supported mode)

## Problem
Memory systems (A-MEM, Mem0, MemoryOS, LangMem) spend most tokens, API calls and time on construction: (1) raw dialogue is redundant, (2) each turn is summarised in isolation or with rigid windows, (3) updates run sequentially during inference, adding latency. The paper targets *construction cost*, not retrieval (retrieval and answer stages are held equal across systems and not measured).

## Mechanism (how it works — concrete, step by step)
1. **Pre-compression** (Light1): LLMLingua-2 (BERT-class token classifier, < 2 GB GPU) keeps tokens whose "retain" probability exceeds the r-th percentile (r = 0.5-0.8). Applied to turns; may be iterated (`x` iterations).
2. **Topic segmentation**: compressed user sentences go into a 512-token sensory buffer; when full, boundaries = intersection of attention-based local maxima (LLMLingua-2 upper layers 8-11, attention sinks masked) and low embedding similarity between adjacent turns. No LLM involved.
3. **Short-term memory** (Light2): topic segments `{topic, {user_i, model_i}}` accumulate in an STM buffer (threshold `th` tokens, 256-1024); when reached, **one LLM summarisation call** per topic group produces entries.
4. **Long-term memory** (Light3): entries are inserted directly with a timestamp ("soft update", no LLM online). Later, for each entry an *update queue* `Q(e_i)` = top-k similar entries with `t_j >= t_i` (only later entries may update earlier ones) is built by vector search; queues are processed by LLM update calls **in parallel** during "sleep".

## Data model (fields, types, statuses, stores; quote exact field names)
`Entry_i = {topic, e_i := embedding(sum_i), user_i, model_i}` plus timestamp and update-queue pairs `(entry_id, similarity)`. Embedding all-MiniLM-L6-v2, cosine retrieval. README adds keywords, entities. Only the *dialogue* timestamp exists: no event time, no validity interval, no status, no importance. Update operations: "add, delete, update, merge".

## Prompts / LLM usage (number of calls, what is LLM vs deterministic code; short excerpts of key prompt wording if available)
LLM only in summarisation (one call per STM flush) and offline update (one call per queued entry that found a related entry). Compression, segmentation, queue building: non-LLM models and vector search. Summary and update prompts are **not in the paper** (only judge prompts). Complexity (their Table 1): calls `O(N r^x T / th)` vs `O(N)` for baselines (N turns, T tokens/turn).

## Evaluation (datasets, metrics, baselines, key numbers incl. tokens / API calls / latency)
LongMemEval-S and LoCoMo, GPT-4o-mini judge; GPT-4o-mini, Qwen3-30B-A3B backbones; baselines FullText, NaiveRAG, LangMem, A-MEM, MemoryOS, Mem0. LongMemEval-S GPT-4o-mini: LightMem 64.3-68.6 vs A-MEM 62.6; online soft-update stage ~28k tokens / 18 calls / 284 s vs A-MEM 1,606k / 987 calls / 5,132 s; offline update adds 47-83k tokens and 70-125 calls (up to 3x the online stage). Headline "up to 38x tokens, 30x calls, 12.4x runtime" is online + offline; "105.9x / 159.4x" is online only. LoCoMo GPT-4o-mini: 71.95 vs A-MEM 64.16, FullText 71.83. Topic-segmentation ablation: -6.3 points (GPT), -5.4 (Qwen). Compression at r 0.5-0.8 keeps QA comparable (in-context test on 1/5 of the data).

## Limitations (as admitted by authors + your own observations)
Authors: privacy and bias risks of stored histories. Ours: (a) accuracy is sensitive to (r, th) non-monotonically (Qwen, th=768: r=0.4 61.9, r=0.6 73.2, r=0.8 64.9) and the headline picks the best of single runs; (b) the offline update did **not** clearly improve accuracy (GPT: +0.4, -2.4, -1.6 points across three settings); its benefit rests on one anecdote (Tokyo/Kyoto); (c) five LongMemEval samples crashed the compressor (corrupted characters) and were counted wrong; (d) dialogue time only — other papers report weak temporal scores for it (LoCoMo temporal F1 20.6 vs 63.5 for MemIR in MemIR's table; TSM reports 74.8 on LongMemEval-S vs LightMem's own 68.6); (e) compression can delete dates, numbers and names; no analysis of that; (f) requires a PyTorch encoder model, awkward for a TypeScript service.

## Implications for Recordare
- **Adopt, important — batching is where the savings come from (D1, D2, D5)**: the win is "one LLM call per buffer flush instead of per turn", not compression. Our idle-debounce window already does this; keep the target of <= 1.2 calls per window and make window size a measured parameter (their th sweep: bigger buffer = fewer calls, accuracy non-monotonic). Report tokens and calls per stored item (H5).
- **Adopt, important — segment long tails by topic before extraction (D1 window bounds, legacy/import mode)**: removing segmentation cost 5-6 points. For tails longer than the window cap (nightly sweep, imports), split on adjacent-turn embedding similarity (the cheap half of their hybrid; skip LLMLingua attention) instead of truncating or cutting at fixed token counts.
- **Adopt — forward-only supersession rule (D28, consolidation)**: only evidence with a later `occurredAt`/message time may supersede earlier facts (`t_j >= t_i`). Use event/message time, not ingestion time, so backfilled or imported conversations cannot overwrite newer facts.
- **Adopt — never let the LLM delete (D6, D28)**: their Tokyo/Kyoto case (two related, non-contradictory items read as a conflict) is the same failure we rejected in Graphiti/Memobase; our `supersedes` / `corrects` keep the old row. Confirms append-only.
- **Avoid, v1 — token pre-compression (LLMLingua-2)**: episodic memory lives on exact dates, numbers, names; compression risk is unmeasured, adds a Python/GPU dependency, and the savings are dwarfed by batching. Revisit only as an opt-in for very long assistant turns.
- **Change, minor — assistant messages (D5, H3)**: LightMem segments and compresses user text only. Our "skip window with no user message" is consistent, but assistant turns must still reach the extractor as context (and for `twin_experienced`, H3).
- **Do not rely on their sleep-time accuracy claim (D8 nightly job)**: offline update was cost-neutral to negative on accuracy and can cost more tokens than the online stage. Justify our consolidation by digests and pattern promotion (D20), with a measured token budget, not by this paper. Keep "zero LLM calls when nothing is new".
